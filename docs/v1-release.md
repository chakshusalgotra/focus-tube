## Implemented Contract

### Chat and Confirmed Notes

- Text chat uses server-held Google Gemini credentials and the pinned `gemini-3.1-flash-lite` model through the official SDK's streaming path. NDJSON delivers provisional text; the legacy final-JSON response remains supported. Only a fully validated final answer can expose actionable citations or a note proposal. Partial, invalid, interrupted, blocked, or unsupported output is not an insertable draft. No provider tools, audio/frame ingestion, voice chat, or automatic billable retries.
- Source permission is required for timed SRT/VTT upload or optional, best-effort public YouTube caption retrieval. Provider consent is required before sending the question, title, captured playhead, selected captions, and conversation context to Google. Existing notebook content, credentials, and other videos are not automatically sent. Caption restrictions are not bypassed; source existence is not proof of answer correctness.
- **Current moment** selects segments overlapping 120 seconds before through 60 seconds after the captured playhead; missing time is not zero. **Whole video** uses the permitted full transcript. Normal follow-ups include the last **four completed exchanges**. **Discussion** snapshots the UI's completed discussion, or explicit completed IDs supplied to the API, plus referenced captions. Oversized context is rejected, never silently shortened to its last turns.
- Limits: sources up to **4 hours / 1 MiB / 10,000 segments**; **50 transcripts / 10 MiB** stored chat content per account; **100 answers** per thread; questions up to **2,000 characters**; input up to **100,000 tokens**, output **1,024 tokens**. One pending request per thread, **5/account/minute**, and a hardcoded **20/account/UTC day**, including administrators. Newly reserved attempts count even when they fail; no daily-cap environment variable exists.
- SQLite reserves maximum estimated generation cost before dispatch and reconciles known usage. Unknown dispatched/canceled usage retains its reservation; Stop is not a refund guarantee. Request-ID replay does not generate again. Source/session/account changes reject stale work. Clearing chat, learning-backup restore, or restart does not reset the cost ledger; deleting an account detaches its ledger ownership.
- **Summarize** generates a proposal; **Add to notes** on a supported completed answer previews it without a second generation. The user can edit, cancel, or explicitly **Append to notes** for the named account/course/video. Natural-language requests cannot authorize a write. Confirmation validates the current source and latest note, appends at the end, preserves manual content, anchors, Read/Edit mode, and history, and groups the append as one immediate Undo step. Source times include zero; discussion-only blocks can be untimed.
- Conflicts, IME composition, changed destinations/sources, and quotas prevent unsafe append. Stable proposal/block IDs prevent duplicate append on confirmation/retry. **Saved to notes** requires the normal notebook server acknowledgement; failed saves retain the normal recovery draft and retry without regeneration. Cancel before append writes nothing; closing an appended preview is not Undo. Chat/Notes share the existing pane; fullscreen remains video-only.
- Schema-3 learning exports round-trip transcripts, completed messages, context, and validated optional proposals. Old messages without proposals and schema-1/2 imports remain supported with explicit missing-data warnings. Exports exclude provider keys, cost ledgers, extension codes/grants/verifiers, and connection state. Clearing chat invalidates its proposals but does not erase already appended notes.

### Chrome Capture

- Plain Manifest V3, **Chrome >=127**, current regular browser profile only. Production is `https://focustube.neuralnest.co.in`; Development is `https://dev-ft.neuralnest.co.in`. Accounts, databases, tokens, and operations are environment-bound; no dual write. Browser profiles do not share extension storage. Use a separate test profile; incognito, Firefox, mobile, and full-playlist capture are excluded.
- Right-click and toolbar flows capture a canonical single-video ID, not page contents, browsing history, or a full FocusTube profile. A successful receipt adds one unstarted course or returns an existing library match without replacing progress/settings/workspace/notes/chat. Profile revision and receipt commit atomically. Same-ID retries reuse the receipt; a retained receipt for a removed item cannot resurrect it.
- Permissions are `contextMenus`, `activeTab`, `storage`, and `identity`, with optional host access to the selected exact HTTPS site. No cookies/history/tabs/scripting/all-sites permission or content scripts. The cookie-first flow uses credentialed requests without reading HttpOnly cookies. When blocked, first-party Connect consent uses single-use code, PKCE S256, state, exact extension ID/origin, and `https://<id>.chromiumapp.org/`. No app window per ordinary save; opening the saved item is optional.
- Codes are hashed, single-use, and valid for at most **5 minutes**. Opaque grants are hashed server-side, scoped to minimal identity/capture/own disconnect, with no refresh token, **30-day maximum and no later than parent-session expiry**. Parent logout, password/email rotation, browser account/session replacement, disabled/deleted accounts, expiry, and successful Disconnect invalidate the affected connection. Cookie/grant mismatch stops capture and requires reconnecting.
- Grants use trusted-context `chrome.storage.local`, not sync or an encrypted vault; PKCE state/verifier use `chrome.storage.session`. Offline Disconnect pauses saving but server revocation remains unconfirmed until retry succeeds or the parent session is invalidated. Removing the extension or host permission alone does not prove server revocation.
- Pending operations: **20 total**, retained for **24 hours**, bound before dispatch and exposed for manual Retry/Discard after popup closure or worker restart. No unbounded silent queue. Receipts: eligible for bounded cleanup after **30 days**, maximum **10,000/account and 100,000/database**; cleanup is not an exact erasure deadline. Pending expiry/Discard does not undo a possibly committed save. Success requires a server receipt.
- Exact allowed Chrome origins are accepted only on enumerated extension POST/preflight routes, after the existing Host/HTTPS-origin checks. The ID is not authorization. Ordinary data/notebook/export/admin routes remain protected and grants cannot access them. Never add Chrome origins to `AUTH_PUBLIC_ORIGINS` or enable HTTP extension access on hosted environments. The explicitly opted-in native loopback exception is described under Temporary Local Testing.

### Member Invitations

- New member invitations default to **7 days** and **1 signup**; the administrator can choose **1/7/30 days or Custom**, with a future expiry at most **365 days** from creation/edit and 1-1,000 signups. Custom input uses the displayed timezone and canonical UTC submission. Existing expiry dates and counts remain unchanged.
- Administration supports create, safe-metadata list (50/page), revision-checked expiry edits, and confirmed revocation. Expired/unexhausted links need explicit `reactivate:true`; revoked/exhausted links cannot be revived. Expiry changes never reset counts or add places. Immediate transactions preserve final-redemption, email-proof, and capacity checks under races.
- Bootstrap stays local-only, one-use/24-hour, and outside browser management. Raw member links are copy-once; hashes cannot reconstruct them. List/edit/revoke never expose the link/token/hash. Records expired for at least 30 days are eligible for cleanup; pruned links cannot be restored. Revocation blocks further signup, not access by members already created.

## Rollout, Backup, and Rollback

These are operator steps, **not executed deployment work**.

1. Obtain approval and freeze the verified source/image/artifact. Record the existing image identity, nonsecret configuration, proxy, loopback ports, project names, data/log volumes, and provider allocations. Preserve existing SMTP and private configuration through the operator's secure process; never print or put them in the release record.
2. Before migration, take a SQLite-aware backup of the intended database, or stop writers and capture a consistent database/WAL set. Preserve the private `.auth-rate-key`, ownership/permissions, and securely retained runtime configuration. A learning JSON export omits sessions, grants, receipts, cost accounting, and shared feedback and is not an operational backup. Test `quick_check` and foreign keys on an isolated restore; compare safe digests instead of credential-bearing rows. Do not reset live counters that advanced legitimately.
3. Rehearse on the disposable populated copy. After approval, use the same tested image/config in development first, with chat/capture initially off. Verify actual public health and account-origin behavior, then authorized feature checks. Production is a separate approval with a fresh backup and its own volume/budget. Do not replace any current local or hosted runtime merely because source files changed.
4. **Kill switches:** recreate the process/container with `VIDEO_CHAT_ENABLED=0` and/or `EXTENSION_ENABLED=0`. `VIDEO_CHAT_MONTHLY_BUDGET_USD=0` also blocks generation; `VIDEO_CHAT_AUTO_CAPTIONS=0` disables automatic caption retrieval, not subtitle upload/chat. These values are read at startup; a plain restart of an unchanged container does not load edited Compose settings. Preserve ledgers and pending reservations; disabling a feature is not a billing refund or data wipe. Revoke individual eligible invites through Administration without opening signup or altering bootstrap rules.
5. **Rollback:** prefer the retained, migration-compatible image with features disabled and the current database intact. Compatibility must include invitation revocation, current session/grant boundaries, and existing data formats; an older image that ignores revocation is unsafe even if it starts. If no compatible rollback exists, keep the features disabled and forward-fix. Restoring an old database is a separate approved recovery decision because it can discard newer learning writes, undo security revocations, and reduce recorded spending. Never silently restore it over new user data or drop the volumes.
